## Chat Server

Минималистичный **TCP‑чат‑сервер** на Java 21, работающий по протоколу **JSON Lines** (один JSON‑объект на строку) поверх `Socket`.  
Сервер обслуживает один процесс клиента‑чата и демонстрирует чистую, модульную архитектуру без тяжёлых фреймворков.

Полная текстовая документация модуля находится в `doc/` (см. ниже раздел **Дополнительная документация**).

## MVP‑функциональность

Сервер реализует небольшой, но законченый функциональный срез:

1. **Аутентификация** по логину и паролю (`AUTH` запрос).
2. **Создание клиентской сессии** и привязка TCP‑подключения к аутентифицированному пользователю.
3. **Отправка сообщений** от одного аутентифицированного пользователя другому (`SEND` запрос).
4. **Доставка сообщений** адресату с использованием push‑событий `INCOMING` (сервер инициирует сообщения сам, без запросов клиента).
5. **Ping / keep‑alive** через `PING` запросы без тела ответа (сервер может не присылать ответ).
6. **Базовая валидация протокола**: проверка обязательных полей, типов, последовательности запросов.
7. **Простая in‑memory модель данных**: никакого диска, БД или истории — всё живёт в ОЗУ до перезапуска процесса.

То, чего **нет** по дизайну:

- **Нет долговременной истории сообщений** — после рестарта сервера все данные теряются.
- **Нет групповых чатов** — только отправка от пользователя к пользователю.
- **Нет статусов присутствия и “печатает…”**.
- **Нет вложений, редактирования или удаления сообщений**.
- **Нет сложной авторизации/ролей** — только факт успешной/неуспешной аутентификации.

## Архитектура

Сервер организован слоями, без Spring/EE, с явной сборкой зависимостей в коде:

- **bootstrap (`com.kstrinadka.chat.server.bootstrap`)**
  - Точка входа `ChatServerApplication#main`.
  - Конфигурация и связывание слоёв в `ApplicationAssembler` и `ServerApplicationContext`.
  - Создание экземпляра `ChatServer` и запуск основного цикла принятия соединений.

- **transport (`com.kstrinadka.chat.server.transport`)**
  - `ChatServer` — основной TCP‑сервер, который:
    - открывает `ServerSocket`,
    - принимает входящие `Socket`‑подключения,
    - создаёт для них `ClientConnection`.
  - `ClientConnection` / `SocketClientConnection` — обёртка над `Socket`, отвечающая за:
    - чтение строк,
    - запись строк,
    - жизненный цикл соединения и обработку закрытия.
  - `ConnectionContext` и `ConnectionContextFactory` — связка TCP‑подключения с пользовательской сессией, состоянием и outbound‑каналом.
  - `OutboundChannel` — небольшая абстракция для отправки `ServerResponse` и push‑сообщений клиенту.

- **infrastructure (`com.kstrinadka.chat.server.infrastructure`)**
  - `JacksonProtocolMessageCodec` — кодирование/декодирование JSON‑строк протокола.
  - `DefaultProtocolValidator` — проверка структуры и обязательных полей входящих запросов до передачи в бизнес‑логику.
  - `DefaultRequestDispatcher` — маршрутизатор, который:
    - по типу `ClientRequest` (`AUTH`, `SEND`, `PING`) вызывает соответствующий use‑case,
    - возвращает `ServerResponse` или `ErrorResponse`.
  - `DefaultAuthenticationService`, `InMemoryUserRepository`, `Sha256PasswordVerifier` — аутентификация и проверка пароля.
  - `DefaultMessageService`, `DefaultMessageDeliveryService`, `UuidMessageIdGenerator` — создание и доставка сообщений.
  - `InMemorySessionRegistry`, `DefaultSessionFactory`, `SessionUnregistrationCloseHandler` — управление сессиями и их автоматическая очистка при закрытии соединений.

- **application (`com.kstrinadka.chat.server.application`)**
  - `AuthUseCase` — сценарий аутентификации пользователя:
    - проверяет логин/пароль через `AuthenticationService`,
    - создаёт серверную `ClientSession`,
    - сохраняет её в реестр активных сессий,
    - возвращает успешный или ошибочный ответ.
  - `SendMessageUseCase` — сценарий отправки сообщения:
    - проверяет, что отправитель аутентифицирован,
    - создаёт новое сообщение через `MessageService`,
    - передаёт его в `MessageDeliveryService` для доставки адресату (в том числе push `INCOMING`).
  - `RequestDispatcher` — контракт маршрутизатора запросов (реализация — `DefaultRequestDispatcher`).
  - `SessionFactory` — контракт для создания серверных сессий.

- **domain (`com.kstrinadka.chat.server.domain`)**
  - `ClientSession` — модель активной пользовательской сессии, связанная с TCP‑подключением и outbound‑каналом.
  - `AuthErrorCode` — перечисление кодов ошибок аутентификации (например, неверный пароль, пользователь не найден).
  - `DeliveryResult` — результат доставки сообщения (получатель онлайн / оффлайн и т.п.).

- **protocol (`com.kstrinadka.chat.server.protocol`)**
  - DTO‑модели запросов и ответов сервера.
  - `ProtocolTypes` — перечисление типов сообщений протокола (`AUTH`, `SEND`, `INCOMING`, `ERROR`, `PING`, и др.).
  - `ClientRequest`, `PingRequest` и другие запросы, которыми оперируют `RequestDispatcher` и use‑cases.

## Жизненный цикл запроса

Упрощённо обработка одного запроса выглядит так:

1. `ChatServer` принимает входящее подключение и создаёт `ClientConnection`.
2. Для каждого соединения запускается цикл чтения строк (line‑delimited JSON).
3. Полученная JSON‑строка передаётся в `JacksonProtocolMessageCodec` для декодирования в `ClientRequest`.
4. `DefaultProtocolValidator` проверяет обязательные поля и типы. При ошибке сразу формируется `ErrorResponse`.
5. Валидный запрос передаётся в `DefaultRequestDispatcher.dispatch(...)`.
6. В зависимости от конкретного подтипа:
   - `AuthRequest` → `AuthUseCase#handle(...)`
   - `SendMessageRequest` → `SendMessageUseCase#handle(...)`
   - `PingRequest` → keep‑alive, может возвращать `null` (ничего не отправляем).
7. Use‑case:
   - обращается к слоям `infrastructure` / `domain`,
   - создаёт `ServerResponse` (или инициирует `INCOMING` push‑событие для другого клиента).
8. `OutboundChannel` сериализует ответ обратно в JSON‑строку и отправляет её через `ClientConnection`.

Подробное текстовое описание потоков и сценариев см. в `doc/request-flow.md`.

## Потоки и конкурентность

- Каждый клиентский `Socket` обслуживается отдельным потоком чтения.
- Внутренние коллекции (реестр сессий, мапы подключений) реализованы так, чтобы быть потокобезопасными для типичных операций:
  - регистрация/удаление сессии,
  - поиск сессии по пользователю или соединению,
  - рассылка/доставка `INCOMING` сообщений.
- При закрытии `Socket`:
  - вызывается `SessionUnregistrationCloseHandler`,
  - cессия удаляется из `InMemorySessionRegistry`,
  - все связанные ресурсы освобождаются.

В этом MVP нет сложного шардинга, балансировки и кластеризации — один JVM‑процесс, один TCP‑порт.

## Ограничения и упрощения

- **Один процесс / один порт.** Нет масштабирования по горизонтали и поддержки нескольких инстансов.
- **In‑memory‑хранение.** Все пользователи и сообщения хранятся только в памяти.
- **Нет персистентности и миграций.** Нет схемы БД, транзакций и т.д.
- **Нет продвинутой безопасности.**
  - Хеширование паролей реализовано упрощённо (через `Sha256PasswordVerifier`) и не претендует на production‑уровень.
  - Нет TLS/SSL: протокол поверх чистого TCP.
- **Ограниченная валидация нагрузки.**
  - Нет квотирования по IP/пользователю,
  - нет продвинутой защиты от DoS.

Все эти ограничения являются **осознанным выбором** для тестового/учебного проекта и задокументированы здесь.

## Стек технологий (первый срез)

- **Язык/Платформа**: Java 21
- **Сборка**: Maven (`server/pom.xml`)
- **Сетевое взаимодействие**: `ServerSocket` / `Socket` (чистый JDK)
- **Сериализация**: Jackson (`ObjectMapper`, JSON Lines)
- **Логирование**: SLF4J / Logback
- **Тесты**: JUnit 5

## Структура пакетов

Ключевые пакеты модуля `server`:

- `bootstrap` — точка входа и сборка приложения.
- `transport` — TCP‑сервер, клиентские соединения, контекст соединения, outbound‑канал.
- `application` — use‑cases (`AuthUseCase`, `SendMessageUseCase`) и общие application‑контракты.
- `domain` — серверные доменные модели и результаты (`ClientSession`, `DeliveryResult`, `AuthErrorCode`).
- `infrastructure` — реализация сервисов, валидация, кодеки, in‑memory‑репозитории, хранилище сессий.
- `protocol` — DTO протокола и типы сообщений.

Более детальное дерево файлов и классов см. в `doc/server-module-tree.md`.

## Как запустить

Из корня репозитория:

```bash
mvn -pl server exec:java
```

Из директории `server`:

```bash
mvn clean compile exec:java
```

По умолчанию сервер слушает один TCP‑порт (см. `ChatServerApplication` и/или `ApplicationAssembler`).  
Клиентский модуль `client` ожидает соответствующие параметры подключения.

## Тесты

- **Smoke‑тесты транспорта**
  - `ChatServerSmokeTest` проверяет базовый запуск/останов сервера и простейший цикл запроса‑ответа.
- **Инфраструктурные тесты**
  - `JacksonProtocolMessageCodecTest` — проверка сериализации/десериализации протокольных DTO.
  - `DefaultProtocolValidatorTest` — проверка валидации входящих запросов и генерации `ErrorResponse`.

Запуск всех тестов модуля:

```bash
mvn test
```

Запуск всех тестов проекта:

```bash
mvn test -pl server,client
```
