# Спецификация API чат-сервера (line-delimited JSON)

Документ описывает **протокол на уровне приложения** модуля `server`: как устроен обмен данными по TCP и как клиенту корректно отправлять запросы и обрабатывать ответы.

Реализация транспорта: `ChatServer`, `SocketClientConnection`. Кодирование сообщений: `JacksonProtocolMessageCodec` (Jackson + `JavaTimeModule`, даты **не** в виде числовых timestamp).

---

## 1. Транспорт и общая модель

| Параметр | Значение |
|----------|----------|
| Протокол | **TCP** (обычный сокет, не WebSocket и не HTTP) |
| Кодировка текста | **UTF-8** |
| Единица обмена | **Одна строка** (`\n` — разделитель записей) |
| Формат строки | **Один JSON-объект** без переводов строк внутри тела |
| Направление | Полный дуплекс: клиент пишет строки запросов, сервер пишет строки ответов **в тот же сокет** |

**Правило клиента:** после `connect` нужно **непрерывно читать строки** из сокета (отдельный поток или async I/O). Сервер может прислать сообщение типа `INCOMING` **в любой момент** после успешной аутентификации, без предшествующего запроса на эту строку — это «push» входящего чата.

**Правило запрос–ответ для инициированных клиентом операций:** на каждую непустую строку запроса сервер, как правило, отправляет **ровно одну** строку ответа **отправителю** (исключение — ситуации обрыва соединения). При операции `SEND` получатель дополнительно получает свою строку `INCOMING` на **своём** соединении.

## 2. Параметры сервера по умолчанию

Значения из `ChatServerApplication` (их можно изменить в коде при сборке/запуске):

| Параметр | Значение по умолчанию |
|----------|------------------------|
| Хост привязки | `0.0.0.0` (все интерфейсы) |
| Порт | `9000` |
| Таймаут чтения сокета | `60000` мс |
| Макс. длина текста сообщения чата (`SEND.text`) | `4096` символов |
| Пользователи (логин → пароль в открытом виде в конфиге, на сервере хранится хеш) | `alice` / `alicepwd`, `bob` / `bobpwd` |

Верхняя граница длины **сырой** строки запроса (весь JSON) на сервере: `max(8192, maxMessageLength + 2048)` — см. `ApplicationAssembler.rawMessageLineLimit`.

## 3. Запросы клиента (`ClientRequest`)

Каждый запрос — JSON с обязательным полем `type`. Поддерживаются только два значения.

### 3.1. `AUTH` — аутентификация

Первое ожидаемое действие на новом соединении. Повторный успешный `AUTH` на уже аутентифицированном соединении даёт ошибку.

| Поле | Тип | Обязательность | Описание |
|------|-----|----------------|----------|
| `type` | string | да, ровно `"AUTH"` | Тип запроса |
| `requestId` | string | да, не пустой | Идентификатор запроса со стороны клиента (для сопоставления ответа) |
| `username` | string | да, не пустой | Имя пользователя |
| `password` | string | да, не пустой | Пароль |

Пример:

```json
{"type":"AUTH","requestId":"1","username":"alice","password":"alicepwd"}
```

### 3.2. `SEND` — отправить сообщение другому пользователю

Доступно только после успешного `AUTH` на **этом** соединении.

| Поле | Тип | Обязательность | Описание |
|------|-----|----------------|----------|
| `type` | string | да, ровно `"SEND"` | Тип запроса |
| `requestId` | string | да, не пустой | Идентификатор запроса |
| `to` | string | да, не пустой | Имя получателя (как в репозитории пользователей) |
| `text` | string | да, не `null`, не пустой, длина ≤ `maxMessageLength` | Текст сообщения |
| `clientMsgId` | string | да, не пустой | Идентификатор сообщения на стороне клиента (дедупликация/отображение в UI) |

Пример:

```json
{"type":"SEND","requestId":"2","to":"bob","text":"Привет!","clientMsgId":"cli-uuid-001"}
```

Имя получателя при поиске сессии дополнительно обрабатывается через `strip()` на сервере (пробелы по краям отбрасываются после прохождения валидации «не blank»).

## 4. Ответы сервера (`ServerResponse`)

Все ответы — один JSON-объект в строке, поле `type` задаёт вид ответа.

### 4.1. `AUTH_OK`

Успешный вход.

| Поле | Тип | Описание |
|------|-----|----------|
| `type` | `"AUTH_OK"` | |
| `requestId` | string | Тот же `requestId`, что в запросе |
| `username` | string | Имя вошедшего пользователя |

### 4.2. `AUTH_ERROR`

Ошибка аутентификации или регистрации сессии.

| Поле | Тип | Описание |
|------|-----|----------|
| `type` | `"AUTH_ERROR"` | |
| `requestId` | string | Из запроса |
| `errorCode` | string | Код ошибки (см. раздел 6) |
| `message` | string | Человекочитаемое пояснение |

### 4.3. `ACK`

Успешная приёмка и доставка исходящего сообщения получателю (на сокет отправителя).

| Поле | Тип | Описание |
|------|-----|----------|
| `type` | `"ACK"` | |
| `requestId` | string | Из запроса `SEND` |
| `serverMsgId` | string | Идентификатор сообщения, назначенный сервером |
| `clientMsgId` | string | Копия из запроса |
| `acceptedAt` | string (ISO-8601 UTC) | Момент создания сообщения на сервере, например `2026-03-28T12:34:56Z` |
| `status` | string | В текущей реализации: `"DELIVERED"` |

### 4.4. `INCOMING`

Входящее сообщение чата для получателя (отправляется на **соединение получателя**, не на соединение отправителя).

| Поле | Тип | Описание |
|------|-----|----------|
| `type` | `"INCOMING"` | |
| `requestId` | null | В реализации всегда `null` (push-событие) |
| `messageId` | string | Серверный id сообщения |
| `from` | string | Отправитель |
| `text` | string | Текст |
| `createdAt` | string (ISO-8601 UTC) | Время создания |
| `clientMsgId` | string | Id сообщения со стороны отправителя |

### 4.5. `ERROR`

Ошибка протокола, бизнес-логики или внутренняя ошибка.

| Поле | Тип | Описание |
|------|-----|----------|
| `type` | `"ERROR"` | |
| `requestId` | string или `null` | Если запрос разобрать нельзя, может быть `null` |
| `errorCode` | string | Код (см. раздел 6) |
| `message` | string | Описание |

## 5. Способы отправки данных клиентом

С точки зрения сервера поддерживается **один** механизм: **запись UTF-8 байтов в TCP-сокет**, где каждый логический запрос заканчивается символом **новой строки** `\n` (LF).

Практические варианты на стороне клиента:

1. **Терминал / скрипт:** `nc`, OpenSSL `s_client`, или любой инструмент «сырого TCP», главное — не искажать UTF-8 и добавлять `\n`.
2. **Стандартная библиотека языка:** `Socket` + `OutputStreamWriter(..., UTF_8)` + `BufferedWriter`: `write(json); newLine(); flush()`.
3. **Высокоуровневые клиенты:** любой фреймворк async (Netty, asyncio и т.д.), если сохраняется модель «строка = JSON + `\n`».

Недопустимо:

- Отправлять несколько JSON в одной строке без `\n` между ними.
- Вставлять неэкранированные переводы строк внутрь JSON (поломает разбиение по строкам).
- Использовать другую кодировку, отличную от UTF-8, для тела протокола.

Чтение ответов: **построчно** (`readLine` / аналог), каждая строка — один JSON.

## 6. Коды ошибок (`errorCode` в `AUTH_ERROR` и `ERROR`)

### 6.1. `AUTH_ERROR.errorCode`

| Код | Когда возникает |
|-----|------------------|
| `INVALID_CREDENTIALS` | Неверная пара логин/пароль, пустые учётные данные |
| `USER_ALREADY_LOGGED_IN` | Пользователь уже имеет активное соединение (реестр сессий не позволяет вторую регистрацию того же `username`) |
| `ALREADY_AUTHENTICATED` | Повторный `AUTH` на соединении, которое уже аутентифицировано |

### 6.2. `ERROR.errorCode` (операции и протокол)

**Бизнес-логика отправки сообщений:**

| Код | Когда возникает |
|-----|------------------|
| `SENDER_NOT_AUTHENTICATED` | `SEND` без предварительного успешного `AUTH` |
| `RECIPIENT_NOT_FOUND` | Пользователь `to` не существует в хранилище пользователей |
| `RECIPIENT_OFFLINE` | Пользователь есть, но нет активного соединения |
| `DELIVERY_FAILED` | Сбой доставки на сокет получателя |
| `INVALID_TEXT` | Некорректный текст (в т.ч. превышение длины на уровне домена) |
| `INVALID_REQUEST` | Некорректные поля сообщения на уровне подготовки (например, внутренние проверки отправителя / `clientMsgId`) |

**Протокол и обработка строк:**

| Код | Когда возникает |
|-----|------------------|
| `EMPTY_REQUEST` | Пустая или пробельная строка запроса |
| `REQUEST_TOO_LARGE` | Сырая строка длиннее допустимого предела |
| `PROTOCOL_ERROR` | Невалидный JSON, нет `type`, неподдерживаемый `type`, ошибки валидации полей |
| `INTERNAL_ERROR` | Необработанное исключение на сервере |
| `UNSUPPORTED_REQUEST` | Запрос не распознан диспетчером (защитный ответ; при штатном codec обычно не доходит) |

## 7. Рекомендуемая логика клиента

1. Установить TCP-соединение на `host:port`.
2. Запустить **цикл чтения строк** в фоне: парсить JSON, различать `AUTH_OK`, `AUTH_ERROR`, `ACK`, `INCOMING`, `ERROR`, сопоставлять по `requestId` там, где он не `null`.
3. Отправить `AUTH` с уникальным `requestId`, дождаться ответа с тем же `requestId`.
4. После `AUTH_OK` можно слать `SEND`. На каждый `SEND` на этом соединении ожидается `ACK` или `ERROR` с тем же `requestId`.
5. Параллельно обрабатывать приходящие `INCOMING` и показывать их в UI.
6. Учитывать `socketReadTimeoutMillis`: при таймауте чтения соединение может оборваться — предусмотреть переподключение.
7. Один зарегистрированный логин — одна активная сессия на сервере (повторный вход с другого клиента получит `USER_ALREADY_LOGGED_IN`, пока первая сессия не закрыта).

## 8. Примеры взаимодействия

Ниже в примерах строки разделены для читаемости; **на проводе** каждый запрос/ответ — одна строка, заканчивающаяся `\n`.

### 8.1. Успешная аутентификация

**Клиент → сервер:**

```text
{"type":"AUTH","requestId":"r1","username":"alice","password":"alicepwd"}
```

**Сервер → клиент:**

```text
{"type":"AUTH_OK","requestId":"r1","username":"alice"}
```

### 8.2. Неверный пароль

**Клиент → сервер:**

```text
{"type":"AUTH","requestId":"r2","username":"alice","password":"wrong"}
```

**Сервер → клиент:**

```text
{"type":"AUTH_ERROR","requestId":"r2","errorCode":"INVALID_CREDENTIALS","message":"Invalid username or password"}
```

### 8.3. Отправка сообщения (два клиента)

**Клиент Alice** уже аутентифицирован и отправляет:

```text
{"type":"SEND","requestId":"r3","to":"bob","text":"Привет, Bob","clientMsgId":"c1"}
```

**Сервер → Alice:**

```text
{"type":"ACK","requestId":"r3","serverMsgId":"<uuid>","clientMsgId":"c1","acceptedAt":"2026-03-28T10:00:00Z","status":"DELIVERED"}
```

(значение `serverMsgId` — реальный UUID, генерируемый сервером.)

**Сервер → Bob** (на сокете Bob, без запроса от Bob):

```text
{"type":"INCOMING","requestId":null,"messageId":"<uuid>","from":"alice","text":"Привет, Bob","createdAt":"2026-03-28T10:00:00Z","clientMsgId":"c1"}
```

### 8.4. Отправка без входа

```text
{"type":"SEND","requestId":"r4","to":"bob","text":"hi","clientMsgId":"c2"}
```

**Сервер → клиент:**

```text
{"type":"ERROR","requestId":"r4","errorCode":"SENDER_NOT_AUTHENTICATED","message":"You must authenticate before sending messages"}
```

### 8.5. Получатель не в сети

После `AUTH` как `alice`:

```text
{"type":"SEND","requestId":"r5","to":"bob","text":"ping","clientMsgId":"c3"}
```

Если `bob` не подключён:

```text
{"type":"ERROR","requestId":"r5","errorCode":"RECIPIENT_OFFLINE","message":"Recipient is offline"}
```

### 8.6. Ошибка протокола (неверный JSON)

**Клиент → сервер:**

```text
not json at all
```

**Сервер → клиент:**

```text
{"type":"ERROR","requestId":null,"errorCode":"PROTOCOL_ERROR","message":"Malformed JSON request"}
```

(точный текст `message` может отличаться в зависимости от причины сбоя разбора.)

## 9. Примеры кода (минимальные)

### 9.1. Bash + `nc` (GNU netcat), одна строка запроса

Убедитесь, что в системе `nc` с поддержкой TCP. Кодировка терминала должна быть UTF-8.

```bash
printf '%s\n' '{"type":"AUTH","requestId":"1","username":"alice","password":"alicepwd"}' | nc 127.0.0.1 9000
```

Ответ сервера может прийти одной строкой в stdout. Для диалога удобнее интерактивный `nc` без конвейера.

### 9.2. Python 3

```python
import json, socket

HOST, PORT = "127.0.0.1", 9000

def send_line(sock, obj):
    data = (json.dumps(obj, ensure_ascii=False) + "\n").encode("utf-8")
    sock.sendall(data)

def read_line(sock):
    buf = b""
    while True:
        ch = sock.recv(1)
        if not ch:
            return None
        if ch == b"\n":
            return buf.decode("utf-8")
        buf += ch

with socket.create_connection((HOST, PORT)) as s:
    send_line(s, {
        "type": "AUTH",
        "requestId": "p1",
        "username": "alice",
        "password": "alicepwd",
    })
    print(json.loads(read_line(s)))

    send_line(s, {
        "type": "SEND",
        "requestId": "p2",
        "to": "bob",
        "text": "Hello from Python",
        "clientMsgId": "py-1",
    })
    print(json.loads(read_line(s)))
```

В реальном клиенте чтение нужно вынести в отдельный поток и обрабатывать `INCOMING`.

### 9.3. Java (фрагмент)

```java
try (Socket socket = new Socket("127.0.0.1", 9000);
     var out = new BufferedWriter(new OutputStreamWriter(socket.getOutputStream(), StandardCharsets.UTF_8));
     var in = new BufferedReader(new InputStreamReader(socket.getInputStream(), StandardCharsets.UTF_8))) {

    out.write("{\"type\":\"AUTH\",\"requestId\":\"j1\",\"username\":\"alice\",\"password\":\"alicepwd\"}");
    out.newLine();
    out.flush();

    String line = in.readLine();
    // разбор JSON (Jackson / Gson / …)
}
```

## 10. Сводная таблица типов по полю `type`

| `type` | Направление | Назначение |
|--------|-------------|------------|
| `AUTH` | клиент → сервер | Вход |
| `SEND` | клиент → сервер | Отправка сообщения |
| `AUTH_OK` | сервер → клиент | Успешный вход |
| `AUTH_ERROR` | сервер → клиент | Ошибка входа |
| `ACK` | сервер → клиент (отправитель) | Сообщение принято и доставлено получателю |
| `INCOMING` | сервер → клиент (получатель) | Входящее сообщение чата |
| `ERROR` | сервер → клиент | Ошибка |
