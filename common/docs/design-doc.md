
Проектирование Java Swing клиента чата поверх TCP и JSON Lines
Требования и рамки MVP
По вашему ТЗ клиент — это desktop‑приложение на Java, которое подключается по TCP к единому серверу и обменивается только текстовыми сообщениями без форматирования, без истории на сервере, без групп, без вложений и без «прочитано». Авторизация — ввод логина и пароля при каждом запуске, регистрации может не быть (достаточно тестовых пользователей). Внешне клиент должен быть максимально похож на тёмный интерфейс Telegram (в пределах MVP и возможностей Swing).

Ключевое техническое ограничение протокола в вашей спецификации — фрейминг сообщений: “одна строка = один JSON‑объект” (newline‑delimited / JSON Lines). Это сильное упрощение транспорта, но оно диктует важные правила реализации: клиент обязан читать сокет непрерывно, потому что сервер может “push”‑нуть входящее сообщение в любой момент после успешной аутентификации, не в ответ на конкретный запрос. Формат JSON Lines широко используется как “одна запись на строку” в потоковой передаче данных.

Важное следствие JSON‑фрейминга: сырые переводы строк внутри JSON‑строк недопустимы, они должны быть экранированы (\n внутри строки JSON). Поэтому для формирования запросов нельзя “склеивать JSON руками” — нужен сериализатор, который корректно экранирует спецсимволы. Даже в описаниях newline‑delimited JSON подчёркивается, что перенос строки выступает разделителем записей, а в строковых значениях он должен быть экранирован.

Что можно сделать “похоже на Telegram” в условиях MVP и данного сервера:

визуальная структура: список диалогов слева, активный чат справа, “шапка” чата, лента сообщений, поле ввода и кнопка отправки;
“семантика” сообщений: пузырьки слева/справа, время, локальный статус “отправляется/доставлено” по ACK (если ваш сервер так отвечает);
минимальные состояния: “не подключен / подключаюсь / авторизация / онлайн / ошибка / переподключение”.
Чего нельзя сделать корректно без расширения протокола (и это нормально честно описать в README):

настоящий список диалогов/последних сообщений/поиск, т.к. сервер не отдаёт историю и не даёт API “список контактов/чатов”;
достоверный online/offline индикатор: сервер не пушит presence‑события, поэтому статус можно узнать лишь косвенно (напр. ошибка RECIPIENT_OFFLINE при отправке).
Это стоит сформулировать как осознанные product‑ограничения MVP, вытекающие из API.

Архитектура клиента и паттерны уровня Senior без переусложнения
Для Swing‑приложений чаще всего выигрывает архитектура семейства Separated Presentation: Presenter/Controller управляет UI через интерфейс View, а доменная логика и сетевой слой отделены. Это повышает тестируемость и снижает “кашу” из listener’ов в формах. В терминологии Oracle и индустрии Swing сам по себе построен на separable models (модели компонентов отделены от представления), поэтому такой подход естественно “ложится” на технологию.

Практичный выбор для тестового:

Passive View: View максимально “глупая” (рендерит и прокидывает события), Presenter делает всю логику; это проще покрывать тестами и хорошо звучит на собеседовании.
Либо компромисс Supervising Controller (часть простейшей логики остаётся во View), но в Swing нет полноценного data binding “из коробки”, поэтому Pure Passive View обычно даёт более предсказуемую структуру.
Рекомендуемая слоистая модель (минимально, но “взросло”):

ui: формы Swing (LoginDialog, MainFrame, панели), кастомные рендереры, темы/стили.
presentation: presenter’ы (LoginPresenter, ChatPresenter), интерфейсы View, маппинг доменных событий в UI‑состояния.
domain: модели (Message, Conversation, User), enum’ы статусов, бизнес‑правила UI‑уровня (например, “не отправлять пустой текст”).
transport/protocol: DTO протокола (AUTH/SEND, ACK/INCOMING/ERROR), codec (JSON ↔ objects).
infra/net: TCP‑клиент, поток чтения, диспетчер ответов, reconnection/backoff.
Почему это хорошо воспринимается работодателем из prop‑trading/финтех‑контекста (вроде Московская биржа): вы демонстрируете контроль потоков, предсказуемость задержек UI, аккуратную многопоточность и separation of concerns — ровно то, что ожидают от “desktop Java engineer” с фокусом на performance и reliability.

Сетевой слой: TCP, JSON Lines, корреляция requestId и push‑события
Потоки и “threading contract” Swing
Swing не потокобезопасен: почти все обращения к компонентам должны происходить на Event Dispatch Thread (EDT), иначе возможны race conditions и ошибки консистентности памяти. Это базовый принцип, который нужно соблюсти, чтобы приложение выглядело “как продакшен”, а не “как учебный пример”.

Отсюда следует обязательная конструкция:

I/O (чтение сокета, парсинг JSON) — в фоновом потоке/Executor.
Обновление UI (добавить сообщение в ленту, показать ошибку) — строго через SwingUtilities.invokeLater(...) или SwingWorker (done/process на EDT).
Каркас соединения
Так как сервер “пушит” INCOMING, клиенту нужен постоянный reader‑цикл. Самый простой надёжный вариант: один выделенный поток, который читает BufferedReader.readLine() и для каждой строки делает decode → dispatch.

Чтобы не блокировать shutdown и уметь детектить “мертвое соединение”, полезно понимать SO_TIMEOUT: если установить socket.setSoTimeout(ms), то блокирующее чтение прервётся SocketTimeoutException, при этом сокет остаётся валидным — можно продолжать цикл и проверять флаг остановки/состояние. Это стандартная семантика Java сокетов.

Корреляция запрос–ответ: requestId → Future
Критическая часть “взрослого” клиента — не “ждать ответ сразу после write()”, а нормально сопоставлять ответы с запросами:

На каждую исходящую операцию (AUTH, SEND) генерируется уникальный requestId.
В PendingRequests хранится Map<requestId, CompletableFuture<ServerResponse>>.
Reader‑поток, получив ответ с requestId != null, завершает соответствующий future.
События без requestId (INCOMING) идут по отдельному каналу: EventBus/Listener на ChatPresenter.
Так вы избегаете гонок, можете отправлять несколько SEND подряд, UI не блокируется, а логика проще тестируется (можно подменить transport моками).

Кодек JSON и java.time
Ваш сервер отправляет времена в ISO‑8601 UTC строках (например, 2026-03-28T10:00:00Z). Чтобы корректно читать/писать Instant/OffsetDateTime, в Jackson обычно подключают модуль JavaTime: JavaTimeModule. В документации модуля показан базовый вызов mapper.registerModule(new JavaTimeModule()).

Также практически важно отключить сериализацию дат как timestamps/массивов и писать строками ISO‑8601 (это совпадает с вашей спецификацией и снижает риск несовместимости). Это делается отключением WRITE_DATES_AS_TIMESTAMPS (пример и объяснение широко приводятся в руководствах по Jackson).

Локальная модель данных (так как сервер не хранит историю)
Поскольку сервер не хранит сообщения, клиент должен держать ленту в памяти:

ConversationStore: Map<String /*username*/, Conversation>
Conversation: List<Message>
Message содержит: direction (IN/OUT), text, createdAt, clientMsgId, serverMsgId, status.
Это позволит реализовать Telegram‑подобный UX: при отправке сообщение появляется сразу в ленте со статусом “sending…”, а по ACK меняется на “delivered”. При ERROR — помечается как “failed” и UI предлагает “повторить отправку”.

UI на Swing с FlatLaf: структура экранов и приёмы стилизации под Telegram Dark
Общий layout, близкий к Telegram
Для Telegram‑подобного интерфейса в Swing хорошо ложится комбинация:

JFrame с BorderLayout (по умолчанию контейнеры верхнего уровня именно так и устроены);
слева — панель “диалоги/контакты” фиксированной ширины;
по центру — панель активного чата;
внутри панелей — BoxLayout (по вертикали) для “шапки + контент + input”.
Oracle‑гайд по layout managers подчёркивает, что BorderLayout — стандарт для верхнего уровня, а BoxLayout удобен для укладки компонентов в строку/колонку.

Вариант “просто и достаточно для тестового”
JPanel внутри JScrollPane, у панели BoxLayout.Y_AXIS, каждое сообщение — кастомный MessageBubblePanel (рисует фон, скругления, текст, время). Это быстрее реализовать, но плохо масштабируется при тысячах сообщений.

Нюанс: renderer в JList — это, по сути, “штамп” для рисования, а не набор живых интерактивных компонентов (поэтому кнопки внутри ячейки не кликаются). Для ленты чата это не проблема, т.к. сообщения в MVP не требуют интерактивности.

Для Telegram‑подобных “пузырьков” рендерер обычно рассчитывает:

перенос слов (JTextArea lineWrap + wrapStyleWord),
ширину пузыря (например, 60–70% от ширины области),
выравнивание: OUT справа, IN слева,
скругления и цвета фона.
FlatLaf как технологическая база “современного Swing”
FlatLaf позиционируется как современный cross‑platform Look-and-Feel для Swing, с темами Light/Dark/IntelliJ/Darcula и поддержкой HiDPI.

Это даёт “современный” вид без написания собственного UI‑пэйнтинга для всего приложения.

Подключение: FlatLaf доступен в Maven Central, что упрощает сборку.

На момент 10 марта 2026 в репозиториях фиксируется версия 3.7.1 как актуальная.

Настройка темы и кастомизация “под Telegram dark”
Основные механизмы кастомизации FlatLaf:

точечная настройка через UIManager.put(key, value) — самый простой способ для небольших изменений;
настройка через .properties‑файлы UI defaults — удобнее, если вы хотите управлять палитрой/отступами централизованно.
подключение пакета с кастомными defaults через FlatLaf.registerCustomDefaultsSource(...) / registerCustomDefaultsSource (описано в API FlatLaf).
Для Telegram‑подобной “мелкой полировки” особенно полезны client properties: это per‑component настройки поведения/вида через JComponent.putClientProperty(). В документации приведены примеры вроде JButton.buttonType = roundRect и настройки scrollbars.

Это удобный приём для “скруглить кнопку отправки”, “сделать input более плоским”, “поджать отступы”, не уходя в кастомный UI.

FlatLaf Extras (доп. модуль) полезен именно в разработке: в нём есть UI inspector и UI defaults inspector, а также поддержка SVG (что упрощает иконки без растрового зоопарка).

Отдельно отмечается, что инспектор defaults не должен попадать в релизные сборки.

Если нужна быстрая подборка “современных тёмных” палитр — можно подключать IntelliJ themes pack как аддон, он поставляется отдельным артефактом и импортирует темы экосистемы JetBrains.

Но для тестового часто достаточно FlatDarkLaf + небольшой набор overrides, чтобы приблизить цвета к Telegram.

Почему не стоит опираться на HTML‑рендеринг Swing для ленты
Соблазн “рисовать сообщения HTML‑ом” через JEditorPane/HTMLEditorKit обычно приводит к проблемам производительности и ограничений рендера: в баг‑трекере OpenJDK существуют старые и известные проблемы “HTML rendering too slow” для JEditorPane.

Для чата надёжнее рендерить пузырьки Swing‑компонентами/графикой.

Maven‑структура проекта, зависимости и упаковка дистрибутива
Рекомендуемая структура репозитория
Чтобы это выглядело как “аккуратный инженерный проект”, самый выигрышный формат — multi‑module Maven:

parent (управление версиями, плагины, форматирование/линтеры при желании),
server (если вы сдаёте сервер вместе с клиентом),

Maven официально документирует стандартный layout каталогов src/main/java, src/main/resources, src/test/java и т.д. — придерживаться его важно для читаемости и “сигнала” интервьюеру, что вы работаете по конвенциям.

Упаковка: fat‑jar vs jpackage
Для тестового обычно достаточно “java -jar”. Но если хочется очень понравиться — покажите понимание современных средств доставки desktop‑приложений:

jlink позволяет собрать кастомный runtime image из модулей; его задача — “assemble and optimize … into a custom runtime image”.
jpackage делает нативные инсталляторы/пакеты; официально описано, что он может паковать модульные и немодульные приложения, а если runtime image не передан, jpackage использует jlink для генерации runtime.
Если же вы делаете fat/uber jar, обратите внимание на нюансы FlatLaf: в README упоминаются требования к Multi‑Release и к корректной обработке META-INF/services при репакаже. Это типичный “подводный камень”, который производит сильное впечатление, когда вы заранее его закрываете.

Скелет проекта и контракты слоёв
Сначала создаётся Maven multi‑module структура и минимальный bootstrap клиента (Main → установка L&F → запуск LoginDialog). Конвенции Maven по layout каталогов держать строго стандартными.

Изучить и зафиксировать threading policy
До написания UI логики нужно принять “контракт потоков”: всё Swing‑обновление — на EDT, I/O — в фоне (Executor/SwingWorker). Это ключевая тема, потому что именно здесь чаще всего “падает качество” новичков в Swing.

Реализовать protocol module и тесты кодека
Делаете DTO запросов/ответов (AUTH/SEND и ответы сервера), Jackson‑codec с JavaTimeModule, отключение timestamps. Добавляете unit‑тесты “JSON из спецификации → объект → JSON обратно” (это очень сильный сигнал зрелости).

Реализовать TCP transport с reader‑циклом и диспетчеризацией
Пишете TcpChatClient:

connect/disconnect;
отдельный поток чтения строк (постоянно);
PendingRequests по requestId;
channel для push‑событий INCOMING.
Для управляемости остановки/таймаутов понимать и при необходимости использовать SO_TIMEOUT.
Собрать UI каркас “Telegram‑like”
MainFrame: левый список (контакты/диалоги), правый чат (header + messages + input). Выбираете layout’ы по назначению (BorderLayout + BoxLayout).

Стилизация FlatLaf под тёмный Telegram
Поднимаете FlatDarkLaf; для точечных отличий используете UI defaults в .properties или UIManager.put. Для отдельных компонентов — client properties.

Если используете отдельный файл overrides — подключаете его через registerCustomDefaultsSource.

Лента сообщений и статусы доставки
Реализуете отображение IN/OUT пузырьков, перенос текста, timestamp, статус “sending/delivered/failed”. Для производительности и “сеньорности” предпочтителен JList с renderer, но можно начать с BoxLayout‑панели и оставить комментарий о tradeoff.

Обработка ошибок протокола как UX‑фича
Ошибка AUTH_ERROR/ERROR — это не “просто лог”: показывайте пользователю понятные состояния (неверный пароль, пользователь уже онлайн, получатель оффлайн). В логах — полный технический текст.

Аккуратная упаковка и документация
Если делаете fat‑jar — учитываете требования FlatLaf к repackaging. Если хотите “wow‑эффект” — добавляете профиль сборки под jpackage (хотя бы как описанный путь в README).
